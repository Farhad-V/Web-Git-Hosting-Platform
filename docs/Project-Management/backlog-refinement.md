# Backlog refinement

Refinement turns a reported problem or proposed capability into an actionable item. It does not authorize implementation, release, or changes to user data by itself.

1. Describe the affected user, trigger, observed behavior, and expected outcome.
2. Identify the requirement, scope boundary, and supporting evidence.
3. Classify the item as defect, improvement, feature, operational work, or documentation.
4. Record dependencies, security/data risks, and acceptance criteria.
5. Choose the smallest coherent delivery slice and appropriate verification.
6. Prioritize with the project owner; keep estimates and dates unset until agreed.
7. After implementation, link the commit, review, test results, and handoff.

An item is ready when its scope and acceptance criteria are clear enough to implement without inventing product decisions. It is complete only when the [delivery criteria](DELIVERY.md) are met. Blocked checks and remaining work stay explicit.

Use the [product backlog](product-backlog.md) and [item template](backlog-items/TEMPLATE.md). Revisit affected items when scope, dependencies, or operational conditions change.
