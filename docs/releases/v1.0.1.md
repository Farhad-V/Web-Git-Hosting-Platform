# GitForge V1.0.1 — Reliability and Security Patch

Release date: 2026-10-10. This patch fixes issues found in a fresh local audit and updates affected dependencies. It retains the owner-centric V1.0.0 product scope and introduces no application database-schema changes.

## What GitForge Provides

GitForge is a self-hosted Git hosting platform built with Laravel 12, React 19, TypeScript, PostgreSQL, and system Git. Its web interface supports registration, session login/logout, repository creation and visibility settings, personal access token management, and branch/commit/tree/text-file browsing. Real Git clients can clone, fetch, and push through Git Smart HTTP.

Public repositories can be read anonymously. Private repositories are owner-only, and only the owner can push to either public or private repositories. Git credentials use a username and personal access token; plaintext tokens are shown once and stored as hashes. Metadata is stored in PostgreSQL; Git history and references live in managed bare repositories addressed by internal repository IDs.

The validated local baseline uses PHP 8.4, Composer 2, PostgreSQL 18, Node.js 24, npm, and system Git. Laravel runs at `127.0.0.1:8000`, and Vite at `127.0.0.1:5173`. The production reference package uses Linux, Nginx, PHP-FPM, HTTPS, and repository storage outside public web roots. Public hosting remains optional for this portfolio/local-use project.

## Fixes

### Preserve pre-existing Git storage on creation failure

The API controller previously attempted filesystem cleanup whenever it had created a repository metadata object. If initialization refused an already existing repository directory, the controller still deleted that directory during compensation, even though the current request had not created it.

Cleanup now runs at the controller level only after the current request successfully initialized storage. The storage service remains responsible for its own partial initialization failures. A controller-level regression checks that a failed creation rolls back new metadata while preserving pre-existing data. This test failed on the original implementation and passes with the fix. Existing rollback and orphan-storage checks also pass.

### Correct production clone URLs

The frontend previously defaulted clone URLs to `http://127.0.0.1:8000`, including production builds. A remote user would therefore be directed to their own computer.

Production now uses the current site's origin. Development retains the local Laravel address. `VITE_GIT_BASE_URL` can override the origin or base path at build time. Tests cover production, development, and explicit overrides; the fresh production bundle contains no localhost Git URL.

### Coordinate backups with paused writes

Taking a database dump and repository archive at different times while writes continue can produce an inconsistent recovery set. Backups now refuse to run unless file-based Laravel maintenance mode is active and the operator explicitly confirms that all writers have been paused and drained.

Before a backup:

1. Run `php artisan down` in the deployed backend using file-based maintenance mode.
2. Wait for in-flight API requests and Git pushes to finish, and pause scheduled jobs and any other direct repository writers.
3. Set `GITFORGE_BACKEND_ROOT` to the deployed backend and set `GITFORGE_BACKUP_WRITES_PAUSED=1` only after verifying that all writers have stopped.
4. Keep writes paused through the database dump, repository archive, and verification. Resume jobs and use `php artisan up` after successful completion if this backup enabled maintenance mode.

The script rechecks maintenance between snapshot steps and removes incomplete staging output on failure. Automated guard tests cover refusal, successful checksummed archive verification, and maintenance ending mid-backup; they run in Deployment Validation.

**Operational change:** Existing backup invocations must supply the two new settings and follow the pause-and-drain procedure. The confirmation is an operator assertion, not an automatic lock on external writers. Maintenance mode alone does not drain requests that already started.

### Documentation and local setup

The empty Git Smart HTTP write analysis document was restored. Deployment guidance, frontend configuration guidance, and the changelog were updated. The audited machine's missing application key was generated in its ignored local `.env`; no key or other secret is included in the release. Other installations must retain their existing application key and complete their own local setup.

## Upgrade

Check out `v1.0.1`, install the locked backend and frontend dependencies, and rebuild the frontend. Clear/rebuild Laravel configuration and route caches as appropriate for the installation. The patch adds no application schema migration. Configure `VITE_GIT_BASE_URL` only when Git HTTP is served from a different public origin or base path.

Preserve the existing `.env`, application key, PostgreSQL data, and managed Git storage. Do not rotate an existing application key merely to upgrade. Review and update backup automation before its next run.

## Remaining Boundaries

The existing production JavaScript chunk-size warning is non-blocking and remains. A full live browser journey and real-data disaster-recovery restore were not performed as part of this patch. Organization/team collaboration, SSH Git transport, distributed Git storage, repository transfer/renaming, and other unimplemented capabilities remain outside the release scope.

The existing `v1.0.0` tag is preserved. This patch does not deploy a public service.
